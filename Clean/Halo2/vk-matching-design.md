Design document for the VK-matching machinery: mechanically re-deriving the ironwood
`VerifyingKey` constraint-system data from a Halo2-Clean `ConstraintSystem` and proving it
equal to the pinned fixture. This discharges the **VK-correctness** seam the requirements
doc names (`halo2-clean-requirements.md:31-33`) and the `-- TODO(VK-correctness)`
assumption ironwood currently trusts verbatim (`Assemble.lean:51-57`: "Lean never
re-derives the verifying key from the Orchard circuit … Discharging it means re-running
keygen from the circuit definition and comparing").

This document proposes the projection pipeline, the comparison mechanism, and the
matching granularity, and enumerates the contested decisions for the maintainer before
code is written. It builds on `lookup-design.md` §5 (lookup VK implications, incorporated
not duplicated) and the selector survey (`halo2-selector-survey.md`).

The hard reference rule carries over: every claim about halo2 (Rust) and ironwood (Lean)
below is read from the actual source — halo2 at `/mnt/data-2tb/zks/halo2/` (tag
`halo2_gadgets-0.5.0`), ironwood at `/mnt/data-2tb/zks/ironwood/` (main) — cited with
file:line, never from memory.

## 1. What the fixture pins (ironwood side, from source)

The pinned fixture is `Zcash/Snark/Fingerprint/Fixture.lean`, header
`-- Auto-generated by halo2 dump_lean_fixture. Do not edit by hand.` (Fixture.lean:1). It
is a single 305 KB file of Lean literals: a `shape : Shape`, a `vk : VerifyingKey shape Fp
G` (with `G := ℕ`, abbrev at Fixture.lean:11), and per-proof data. Only a subset of `vk`
is **constraint-system data** (VK-matching's target); the rest is per-proof
commitments/evals (fingerprint-matching's target, `Fingerprint/Match.lean`, out of scope
here).

### 1.1 The `VerifyingKey` structure

`Zcash/Snark/Verifier/Assemble.lean:64-79`:

```lean
structure VerifyingKey (shape : Shape) (F G : Type*) where
  omega : F                                         -- domain generator
  n : ℕ                                             -- domain size 2^k
  blindingFactors : ℕ
  delta : F
  chunkLen : ℕ
  gates : List (Expr F)                             -- ← CS data
  instanceQueryLayout : List (ℕ × ℤ)                -- ← CS data
  adviceQueryLayout : List (ℕ × ℤ)                  -- ← CS data
  fixedQueryLayout : List (ℕ × ℤ)                   -- ← CS data
  fixedCommitment : ℕ → G                           -- commitments (deferred, §Phase 2)
  instanceCommitment : Fin shape.numProofs → ℕ → G
  permutationCommonCommitment : Fin shape.numPermutationColumns → G  -- commitments
  permutationChunks : List (List (ColumnRef × ℕ))   -- ← CS/layout data
  lookupInputExprs : Fin shape.numLookups → List (Expr F)   -- ← CS data
  lookupTableExprs : Fin shape.numLookups → List (Expr F)   -- ← CS data
```

The **CS-data fields** — the ones a Halo2-Clean `ConstraintSystem` must reproduce — are:
`gates`, `{instance,advice,fixed}QueryLayout`, `permutationChunks`, `lookupInputExprs`,
`lookupTableExprs`, plus the scalar counts in `shape` (below). The `*Commitment` fields
are Pallas MSMs over the fixed/permutation polynomials; recomputing them in Lean is
explicitly out of scope (`halo2-clean-requirements.md:273-274`) and rests on ironwood's
capture. So the achievable VK-matching target is the **symbolic** CS data, not the
committed data.

### 1.2 The `Shape` counts

`Zcash/Snark/Core/ProofString.lean:39-50`, and the fixture's concrete values
(Fixture.lean:15) for the Orchard action circuit:

```lean
structure Shape where
  k, numProofs, numAdviceColumns, numLookups, numPermutationSets,
  numPermutationColumns, numQuotientPieces, numInstanceQueries,
  numAdviceQueries, numFixedQueries, numPointSets : ℕ

-- action circuit:
{ k := 11, numProofs := 1, numAdviceColumns := 10, numLookups := 3,
  numPermutationSets := 3, numPermutationColumns := 15, numQuotientPieces := 8,
  numInstanceQueries := 1, numAdviceQueries := 25, numFixedQueries := 29, numPointSets := 5 }
```

Note there is **no `numSelectors` field and no `selectors` field anywhere** in `Shape` or
`VerifyingKey`. This is the first half of the selector-compression finding (§2):
selectors do not survive into the fixture as selectors.

### 1.3 The `Expr` type and the query-index indirection

`Zcash/Snark/Verifier/Expressions.lean:29-51`:

```lean
inductive Expr (F : Type*) where
  | constant : F → Expr F
  | fixed    : ℕ → Expr F        -- ℕ is a QUERY INDEX, not a column
  | advice   : ℕ → Expr F
  | instance : ℕ → Expr F
  | negated  : Expr F → Expr F
  | sum      : Expr F → Expr F → Expr F
  | product  : Expr F → Expr F → Expr F
  | scaled   : Expr F → F → Expr F

def Expr.eval (fixedEvals adviceEvals instanceEvals : ℕ → F) : Expr F → F
  | .fixed i => fixedEvals i        -- resolves the index against the eval table
  | .advice i => adviceEvals i
  | ...
```

**Load-bearing:** `Expr.fixed/advice/instance` carry a **query index** `i : ℕ`, *not* a
`(column, rotation)` pair. The `(column, rotation)` lives in the corresponding
`*QueryLayout : List (ℕ × ℤ)`, at position `i`. E.g. from the fixture:

```lean
adviceQueryLayout := [(0,0), (1,0), …, (9,0), (9,1), (9,-1), (2,1), …]   -- Fixture.lean:25
fixedQueryLayout  := [(3,0), (0,0), (11,0), (4,0), …, (28,0)]            -- Fixture.lean:26
```

so `.advice 10` in a gate means "the query at index 10", which `adviceQueryLayout[10] =
(9, 1)` resolves to "advice column 9, rotation +1". This indirection is exactly what
Halo2-Clean's `Query` type does *not* have: Halo2-Clean gates carry `Query.advice col rot`
(column + rotation directly, `Expression.lean:97-102`), with query indices "assigned by a
deterministic first-encounter walk … at VK-compilation time" (`Expression.lean:93-96`,
`Configure.lean:16-19`) — a walk that does not yet exist in code. Producing the
`*QueryLayout` lists and rewriting `Query` atoms to indices **is** that walk. This is the
core of the projection pipeline (§3).

### 1.4 Ironwood defers lookup and permutation combinatorial soundness

`Zcash/Snark/Soundness/Constraints.lean:24-27`: the vanishing-check soundness "establishes
**gate** satisfaction … It does not connect the permutation and lookup terms to the
circuit-level copy and lookup constraints … that is separate (#14)." So VK-matching's job
is purely the *symbolic identity* of the CS data — it does not and need not touch the
combinatorial semantics (that is the `lookup-design.md` `enableLookup` bridge and the
permutation bridge, both joint work). This keeps VK-matching a clean, decidable,
data-only obligation.

## 2. The selector-compression finding (the central modeling decision)

**Verdict: the fixture is POST-compression. Selectors do not appear in the fixture at all;
each was folded into a fixed column, and every gate/lookup expression that referenced a
selector now references that fixed column through a root-finding polynomial. Reproducing
the fixture therefore requires running selector compression as part of the projection —
and compression is a global function of the whole circuit's floor-planned selector
activations.** Evidence, in three layers:

### 2.1 halo2 builds the VK *after* compressing selectors

`halo2_proofs/src/plonk/keygen.rs` (`keygen_vk`):

```rust
let (cs, selector_polys) = cs.compress_selectors(assembly.selectors);   // :222
fixed.extend(selector_polys.into_iter().map(...));                       // :223-227
…
.build_vk(params, &domain, &cs.permutation);                            // :231 (uses compressed cs)
…
VerifyingKey::from_parts(domain, fixed_commitments, permutation_vk, cs) // :~242 (compressed cs)
```

The `cs` that ends up in the `VerifyingKey` is the **return value of
`compress_selectors`**, not the pre-compression one. `assembly.selectors` (the per-selector
per-row activation table) is produced by running the floor planner / synthesis first
(keygen.rs:208, :214-219).

### 2.2 What compression does to expressions

`compress_selectors` (`circuit.rs:1232-1276`):

1. Packs **disjoint** simple selectors into shared new fixed columns. Two selectors are
   *excluded* from sharing a column iff they are ever both enabled on the same row
   (`compress_selectors.rs:100-124`, the `exclusion_matrix`: `l & r` over
   `activations`). Compatible selectors get distinct nonzero "root" values `1, 2, 3, …`
   in one column; a disabled row is `0`.
2. Substitutes every `Expression::Selector(k)` in every gate polynomial with the
   expression (`compress_selectors.rs:184-201`, `replace_selectors` at circuit.rs:1294-1322):

   ```
   q · Π_{i = 1..=combination_len, i ≠ assigned_root} (i − q)
   ```

   where `q` is a `Fixed` query on the packed column. This polynomial is nonzero exactly
   on rows where the packed column equals `assigned_root` (i.e. selector `k` is on).

This is directly visible in the fixture. The first gate (Fixture.lean:16) is

```lean
.product (.product (.product (.product (.product (.product
  (.fixed 18)
  (.sum (.constant 2) (.negated (.fixed 18))))     -- (2 − q)
  (.sum (.constant 3) (.negated (.fixed 18))))     -- (3 − q)
  (.sum (.constant 4) (.negated (.fixed 18))))     -- (4 − q)
  (.sum (.constant 5) (.negated (.fixed 18))))     -- (5 − q)
  (.sum (.constant 6) (.negated (.fixed 18))))     -- (6 − q)
  (.sum (.sum (.advice 0) (.negated (.advice 1))) (.negated (.product (.advice 2) (.advice 3))))
```

i.e. `q·(2−q)(3−q)(4−q)(5−q)(6−q) · poly` — `assigned_root = 1` out of a **6-selector
combination** packed into fixed-query index 18. The lookup inputs show the same:
`lookupInputExprs` reference `.fixed 14/15/16` (Fixture.lean, `lookupInputExprs`) where the
range-check `q_lookup`/`q_running` complex selectors were.

### 2.3 The pinned CS strips gate names and compares raw polynomials

`PinnedConstraintSystem` (`circuit.rs:966-979`) carries `gates: PinnedGates`, whose `Debug`
flattens to `gate.polynomials()` only (`circuit.rs:981-990`) — gate names and
constraint-name structure are dropped; the VK fingerprint is the **flat list of
constraint polynomials**, matching ironwood's `gates : List (Expr F)`. `num_selectors` is
still a field of `PinnedConstraintSystem` (circuit.rs:970) but is dev-tooling only and
does *not* appear in the ironwood fixture — consistent with §1.2.

### 2.4 Consequence: compression is whole-circuit and layout-dependent

The exclusion matrix (§2.2.1) is built from the **complete activation table of every
selector across every row** — which is the floor planner's output for the entire circuit.
Which selectors share a column, what root each gets, and hence *which fixed-query index
and which disambiguation polynomial* each gate ends up with, are all global functions of
the whole assignment. **There is no compression of a single gadget in isolation** that
agrees with the full-circuit fixture: a gadget's selector might pack with a selector from
a completely unrelated gadget. This is the crux of the granularity verdict (§5).

## 3. The projection pipeline

Target: a total function `projectVK : ConstraintSystem F → LayoutData → VerifyingKeyCS F`
producing ironwood-shaped CS data, provably equal to the fixture's. It has two stages: a
**pre-compression** stage that is pure `ConstraintSystem` data (layout-independent), and a
**compression + query-walk** stage that consumes layout data. The stages matter because
the first is the sub-circuit-matchable part (§5) and lands cleanly; the second is
whole-circuit and needs the floor planner (Phase 2 territory).

### 3.1 Stage A — pure `ConstraintSystem` projection (layout-independent)

From `Configure.lean:100-110`, a Halo2-Clean `ConstraintSystem` already accumulates, in
call order: `numAdviceColumns`, `numFixedColumns`, `numInstanceColumns`, `numSelectors`,
`gates : List (Gate F)`, `lookups : List (LookupArgument F)`, `permutationColumns : List
AnyColumn`, `constants : List (Column .fixed)`. Stage A projects:

- **`gates` (pre-compression):** flatten `cs.gates` to `List (Expression F Query)` by
  concatenating each gate's `constraints.map (·.poly)` in gate order (mirroring
  `PinnedGates`' `flat_map(polynomials)`, §2.3). At this stage the polys still contain
  `Query.selector s` atoms — this is the *raw* gate list, matchable against a
  raw-selector fixture fragment but **not** against the compressed fixture.
- **`lookups`:** already the right shape — `LookupArgument { inputs, tables : List
  (Expression F Query) }` (`Configure.lean:91-93`) maps directly to
  `(lookupInputExprs, lookupTableExprs)` per lookup, indexed by registration order
  (`Fin numLookups`). This is `lookup-design.md` §5.1 verbatim; nothing new. Table sides
  are already rotation-0 fixed queries (`lookup.rs` wrap, `Configure.lean:170-173`),
  matching the fixture's `.fixed 1`, `.fixed 11`, `.fixed 12`.
- **Counts:** `numAdviceColumns → shape.numAdviceColumns` directly. `numInstanceColumns →`
  used in `numInstanceQueries` accounting. `numFixedColumns` is *pre-compression* and must
  be **grown** by the number of packed selector columns in Stage B before it equals the
  fixture's 29 (§3.3).

Stage A is a fold over the `ConstraintSystem`, deterministic, and layout-free. The only
uncontested code this document proposes to land are the *data* pieces of Stage A (a
`VerifyingKeyCS` record mirroring the ironwood field types, and the raw-gate flatten) —
see §7.

### 3.2 Stage B — the first-encounter query-index walk

Ironwood's `Expr` uses query indices (§1.3); Halo2-Clean's `Query` uses column+rotation.
The bridge is halo2's first-encounter walk (`circuit.rs:1081-1110`,
`query_{fixed,advice,instance}_index`): walking the finished expression set in a fixed
order, each *new* `(column, rotation)` gets the next index and is appended to the query
list; repeats reuse the index. Registration order = expression-traversal order.

The projection reproduces this: walk the projected gate polys and lookup exprs in halo2's
order, building `{fixed,advice,instance}QueryLayout : List (ℕ × ℤ)` and simultaneously
rewriting each `Query.advice col rot` to `Expr.advice idx` (via `Expression.mapVar`,
`Expression.lean:237-242`, exactly the "project to bare query-index variables" the erasure
note anticipates). The erasure of the 4-node `Expression` to ironwood's 8-node `Expr`
(mapping `mul (const (-1)) ·↦ negated`, `mul · (const c) ↦ scaled`, etc.) happens in the
same pass (`Expression.lean:104-109`, requirements doc §"Two-layer DSL").

**Ordering risk (from `lookup-design.md` §5.3):** the walk must include lookup input/table
expressions in the same relative order halo2 does, or every downstream index shifts. This
is a VK-compiler correctness obligation, gotten right by matching halo2's traversal, not a
semantics question. It is the fiddliest part of the pipeline and the highest-value target
for a `native_decide` cross-check against the fixture (§4).

### 3.3 Stage B — selector compression

This is where the pipeline needs layout data and stops being sub-circuit-local. Given the
per-selector activation table (floor-planner output), run the §2.2 algorithm:
build the exclusion matrix, greedily pack disjoint selectors into new fixed columns
(assigning roots), grow `numFixedColumns` by the packed-column count, and substitute each
`Query.selector s` in the projected gates/lookups with the root-finding polynomial
`q·Π(i−q)` over the packed column's fixed query. *Then* the query-walk (§3.2) runs over the
substituted expressions (halo2 does it in this order: compress at keygen.rs:222, and the
fixed_queries the substituted `Fixed` atoms register are allocated inside
`compress_selectors` via `query_fixed_index`, circuit.rs:1268-1273).

**Do we need compression for fixture comparison?** For the *whole-circuit action-circuit
fixture as it exists today* — yes, unavoidably: the fixture is post-compression (§2) and
there is no pre-compression artifact to compare against. For *sub-circuit porting-time
tooling* — no, and we should deliberately avoid it (§5): compression is precisely the
whole-circuit, layout-dependent step that a gadget-level check cannot and should not run.

### 3.4 Permutation projection (scope only; detail in Phase 2)

`permutationChunks : List (List (ColumnRef × ℕ))` (Assemble.lean:77) pins the copy-enabled
columns grouped into sets, each column paired with its common-eval index. The fixture
(Fixture.lean, `permutationChunks`):

```lean
[[(.instance 0, 0), (.advice 0, 1), …, (.advice 4, 5)],           -- set 0 (7 cols)
 [(.advice 6, 7), …, (.advice 9, 10), (.fixed 0, 11), (.fixed 7, 12), (.fixed 8, 13)],  -- set 1
 [(.fixed 9, 14)]]                                                  -- set 2
```

The **column set and its order** come directly from Halo2-Clean's
`ConstraintSystem.permutationColumns` (accumulated in `enable_equality`/`enable_constant`
call order, `Configure.lean:107-108, 139-148`) — this part is Stage A data and matchable
now. The **chunking into sets** is a keygen detail (columns grouped by `chunkLen`,
`permutation/keygen.rs`), and the actual permutation *commitments* (the copy-constraint
cycle mapping over floor-planned rows, `permutation/keygen.rs:102-153`) are Pallas MSMs —
out of scope (§Phase 2). So VK-matching can reproduce `permutationChunks`' **symbolic
structure** (which columns, in which sets) but not the committed permutation polynomials.

## 4. The comparison mechanism

Three candidate mechanisms; recommendation is a **`native_decide` theorem** at
whole-circuit granularity plus **`#eval` golden diagnostics** for incremental porting.

### D-COMP. How to compare projected CS against the fixture  *(recommend: `native_decide` theorem; `#eval` for dev loop)*

- **Option A — `#eval`-style golden test.** `#eval projectVK myCS == Fixture.vk.cs` (or a
  pretty-printed diff), run in CI as a script.
  - *Pro:* zero trust-base impact; fastest dev loop; a diff pinpoints the first mismatched
    gate/query, which is what a porter needs.
  - *Con:* not a proof — a green `#eval` is a test, not a theorem; the VK-correctness seam
    (`requirements:31-33`) asks for *proof* of equality. Also `#eval` on 305 KB of literals
    can be slow without `native`.
- **Option B — `decide`/`native_decide` theorem (recommended).**
  `theorem action_vk_matches : projectVK actionCS layout = Fixture.vk.gates ∧ … := by
  native_decide`, over `DecidableEq` on the `Expr`/layout data (ironwood's `Expr` has no
  `DecidableEq` derive yet — a trivial add; Halo2-Clean's `Expression` and `Query` already
  `deriving DecidableEq`, `Expression.lean:102,115`).
  - *Pro:* an actual theorem discharging the seam; `native_decide` handles the 305 KB
    comparison in reasonable time (it is a flat structural equality, the same style
    ironwood's own `Fingerprint/Match.lean` fixture match uses — "The numeric fixture
    match (`native_decide`)", Match.lean:29).
  - *Con:* `native_decide` enlarges the trust base (compiler + `Decidable` instance
    correctness). Acceptable here and precedented: ironwood *already* uses `native_decide`
    for its fingerprint match (Match.lean:29), so VK-matching adds no new trust category.
    A plain `decide` is likely too slow at this size; `native_decide` is the pragmatic
    choice, matching ironwood's own practice.
- **Option C — generated-fixture round-trip.** Have Halo2-Clean itself *emit* a fixture
  and diff it against the halo2-dumped one textually (outside Lean).
  - *Con:* moves the comparison out of the proof assistant entirely; strictly weaker than
    B and no cheaper than A for the dev loop. Rejected.

Recommendation: **B for the seam-discharging theorem, A as the everyday porting
diagnostic.** They share `projectVK`; A is just B's decision procedure run for its
counterexample rather than its truth value. Land A's `#eval` harness first (it needs only
Stage A + the walk, and gives immediate porting feedback), promote to B once `projectVK`
is complete and the walk is validated.

### 4.1 Trust base and CI

- `projectVK` must be **computable** (no `Classical.choice`) — already required for VK
  compilation generally (`requirements:198-201`). The extractor/knowledge-soundness axis
  imposes the same constraint, so this is free.
- The fixture itself is trusted verbatim (it *is* the deployed VK capture; the "same ℕ tag
  ⇔ same Vesta point" faithfulness lives in the Rust capture, Match.lean:45-46). VK-matching
  does not and cannot reduce that trust; it discharges only the *Lean-side* re-derivation
  (`Assemble.lean:51-57`).
- CI cost: one `native_decide` over 305 KB per circuit. Incrementality is *not* free at
  whole-circuit granularity (§5) — every gadget change re-runs the whole match. This is the
  motivation for the sub-circuit diagnostic layer.

## 5. Granularity: sub-circuit matching (the porting-time verdict)

The maintainer wants VK-matching as **porting-time tooling** — able to check a single
gadget's contribution as it is ported, not only the whole action circuit at the end. The
survey gives a sharp, source-grounded verdict:

**Exact fixture matching is intrinsically whole-circuit, because selector compression
(§2.4) makes the compressed gate/lookup expressions and the fixed-query indices global
functions of the entire circuit's floor-planned selector activations. A single gadget's
gates cannot be compressed in isolation to agree with the fixture. BUT the
*pre-compression* CS data (raw gates with `Query.selector` atoms, raw lookups, column
counts, permutation column set) IS a compositional, gadget-local projection, and sub-circuit
matching should be designed at that pre-compression layer — as a *subset/fragment* check,
not against the compressed fixture.**

Concretely, two matchable granularities:

1. **Whole-circuit, post-compression (the seam):** `projectVK actionCS layout == Fixture` —
   the §4 `native_decide` theorem. This is the only granularity that touches the actual
   fixture, and it only exists once the full circuit is ported and the floor planner is
   modeled (Phase 2). It is the *end* of porting, not a porting aid.

2. **Sub-circuit, pre-compression (the porting aid, recommended to design for):** each
   ported gadget's `configure` produces a `ConstraintSystem` fragment; project it through
   **Stage A only** (raw gates, lookups, column/selector counts — no compression, no
   whole-circuit walk) to a `VerifyingKeyCS`-fragment over `Query.selector`-carrying
   expressions. Then check that fragment is a **subset** of a *pre-compression reference*.
   Two sources for that reference:

   - **(a) A pre-compression fixture dump.** Ask ironwood/the Rust side to also dump the
     `ConstraintSystem` *before* `compress_selectors` (a second `dump_lean_fixture` call at
     keygen.rs:221, before :222). This raw dump has selectors intact and is directly
     comparable to Stage-A gadget fragments (`gate polys ⊆ rawGates`, `lookups ⊆
     rawLookups` up to the gadget's registration slice). **This is the highest-leverage
     ask of this document** — a one-line capture change unlocks gadget-level VK regression
     during porting. Recommended.
   - **(b) Structural self-consistency only.** Absent a raw dump, check gadget fragments
     against each other / against hand-specified expected gate ASTs (a golden `#eval` per
     gadget, no fixture). Weaker (no tie to the deployed VK) but needs no Rust change and
     still catches "this port's gate AST drifted" regressions — the region-faithfulness
     class of bug (`requirements:171-180`).

   The subset check is decidable (`native_decide` over `List.Sublist`/membership on
   `DecidableEq` expressions) and composes: the whole-circuit raw gate list is the ordered
   concatenation of the gadgets' fragments, so `⋃ gadget fragments = rawGates` is itself a
   provable lemma, bridging (2) to (1)'s pre-compression half.

Why subset and not equality at sub-circuit level: a gadget contributes *some* gates and
lookups to the global CS, but the global CS also contains other gadgets' contributions and
the compression rewrite. Equality only holds for the whole circuit; a fragment is a
sublist. This mirrors how `lookup-design.md` chose a *subset* (membership) relation for
the lookup semantics itself — the VK side inherits the same "fragment ⊆ whole" shape.

**Verdict summary:** design the porting-time tool at the **pre-compression, sub-circuit,
subset-check** layer (2), backed ideally by a raw pre-compression fixture dump (2a). Keep
the compressed whole-circuit `native_decide` (1) as the final seam-discharging theorem.
Do not attempt to compress sub-circuits against the compressed fixture — it is not
well-defined.

## 6. Decision points

### D1. Comparison mechanism  *(recommend: `native_decide` theorem + `#eval` diagnostic, §4)*

`native_decide` whole-circuit theorem discharges the seam and matches ironwood's own
fixture-match practice (Match.lean:29); `#eval projectVK == fixture` is the porter's daily
diff. Both share `projectVK`. See D-COMP above for the full trade-off.

### D2. Matching granularity  *(recommend: pre-compression sub-circuit subset check, §5)*

Design the porting-time tool at the pre-compression, gadget-local, subset layer; keep the
compressed whole-circuit equality as the final theorem. Do **not** compress sub-circuits.

### D3. Pre-compression fixture dump  *(recommend: request it — highest leverage, §5.2a)*

Ask the Rust capture to emit the `ConstraintSystem` *before* `compress_selectors`
(keygen.rs:221) as a second `dump_lean_fixture`. One-line change; unlocks gadget-level VK
regression tied to the real circuit during porting, without modeling the floor planner.
If declined, fall back to structural golden `#eval`s per gadget (§5.2b).

### D4. Where selector compression is modeled  *(recommend: Phase 2, layout-coupled, §3.3)*

Compression needs the full activation table (floor-planner output). Model it in Phase 2
alongside the floor planner, not now. The Stage-A/Stage-B split (§3) is designed so that
everything landable-now (raw projection, the data record, the query-walk over raw exprs)
sits before the compression boundary.

### D5. `projectVK` output type  *(recommend: mirror ironwood's field types exactly, §7)*

Define a `VerifyingKeyCS F` record whose fields are ironwood's CS-data fields with
ironwood's types (`gates : List (Expr F)`, `*QueryLayout : List (ℕ × ℤ)`,
`lookup{Input,Table}Exprs`, `permutationChunks`, the counts). Comparison is then structural
equality against a projection of `Fixture.vk`. Using ironwood's own `Expr`/types (once
clean2 imports ironwood, `requirements:44-46`) avoids a second erasure at the boundary.
Until the import lands, a locally-vendored `Expr` mirror is fine (the erasure target is
already specified, `Expression.lean:104-109`).

### D6. Query-walk faithfulness  *(recommend: validate against fixture query layouts first, §3.2)*

The first-encounter walk is the subtlest correctness point (index shifts cascade). Land it
early and validate it in isolation: project only the query layouts and `native_decide` them
equal to `Fixture.vk.{advice,fixed,instance}QueryLayout` before trusting the full gate
projection. The query layouts are small (25/29/1 entries) and a mismatch there localizes
the walk bug precisely.

## 7. Uncontested data definitions (may land as code)

Only the *data-shape* pieces are uncontested — they mirror ironwood's field types and
carry no semantics or contested design. Everything else (the walk, compression, the
comparison theorems, the sub-circuit subset machinery) awaits sign-off. Landable now:

- A `VerifyingKeyCS F` record (or reuse ironwood's `VerifyingKey` CS-field subset) as the
  `projectVK` codomain, per D5.
- The **Stage-A raw gate flatten**: `cs.gates.flatMap (·.constraints.map (·.poly)) :
  List (Expression F Query)` — pure `ConstraintSystem` data, the pre-compression gate list.
  Mirrors `PinnedGates`' `flat_map(polynomials)` (circuit.rs:981-990). No selectors
  substituted, no indices assigned — just the flatten.
- The **lookup projection** is already done: `ConstraintSystem.lookups : List
  (LookupArgument F)` with `{inputs, tables}` maps element-for-element to
  `(lookupInputExprs, lookupTableExprs)`; this landed with the lookup data fix
  (`lookup-design.md` §6). Nothing to add.

No query-walk, no compression, no comparison theorem, and no sub-circuit subset machinery
land until D1–D6 are settled — those are the design core this document exists to review.

## 8. Rust/ironwood findings that surprised / constrain the design

- **The fixture is post-selector-compression, and there is no `selectors` field in it at
  all.** Selectors became fixed columns via root-finding polynomials `q·Π(i−q)`; the
  fixture's first gate literally shows a 6-selector combination packed into `.fixed 18`.
  Any exact fixture match must run compression — a whole-circuit, layout-dependent step
  (§2). This is the single biggest constraint: it forces the sub-circuit tool onto a
  *pre-compression* layer (§5).
- **Selector compression is a global function of the entire circuit's activation table.**
  Which selectors pack together depends on which are ever co-enabled on a row
  (`compress_selectors.rs:100-124`), across all gadgets. So "compress this gadget" is not
  well-defined — the granularity verdict follows directly from this, not from a modeling
  preference.
- **Ironwood's `Expr` uses query *indices*, not (column, rotation).** The projection must
  run halo2's first-encounter query-registration walk to assign indices and emit the
  `*QueryLayout` lists (§1.3, §3.2). Halo2-Clean's `Query` carries column+rotation and
  *no* index by design (`Expression.lean:93-96`) — the index assignment is exactly the
  missing VK-compiler step.
- **The pinned gate list is name-stripped and flat** (`PinnedGates` → `flat_map
  polynomials`, circuit.rs:981-990), matching ironwood's `gates : List (Expr F)`. Gate and
  constraint *names* are not VK data — good, since Halo2-Clean carries them
  (`Configure.lean:48-52`) but they need not match.
- **The committed VK data (fixed/permutation commitments) is out of reach in Lean**
  (Pallas MSMs, `requirements:273-274`); VK-matching reproduces only the *symbolic* CS
  data. The permutation *column set/order* is matchable (Stage A), but the permutation
  *commitment* (cycle mapping over floor-planned rows) is not (§3.4).
- **Ironwood already trusts the fixture verbatim and flags exactly this seam**
  (`Assemble.lean:51-57`, `-- TODO(VK-correctness)`), and already uses `native_decide` for
  its sibling fingerprint match (Match.lean:29). So the recommended mechanism (§4) adds no
  new trust category and closes a seam ironwood explicitly left open.
- **Ironwood defers lookup/permutation combinatorial soundness (#14,
  `Soundness/Constraints.lean:24-27`).** VK-matching is purely symbolic CS-data identity;
  it does not touch — and is cleanly independent of — that deferred soundness bridge. The
  two seams (VK-correctness, semantic adequacy) stay separate exactly as
  `requirements:30-37` frames them.
